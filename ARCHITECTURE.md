# Mavo architecture

Mavo begins as a modular monolith: one desktop application, one local backend, and one durable database. Domain modules can evolve independently without introducing operationally expensive local microservices.

## Milestone 1 runtime

```text
Tauri host
  ├─ React webview
  │    └─ authenticated HTTP → 127.0.0.1:<random port>
  └─ managed Python sidecar
       ├─ FastAPI
       ├─ SQLAlchemy → SQLite (WAL)
       └─ Model Router
            ├─ Ollama on 127.0.0.1:11434
            ├─ OpenAI Responses API
            ├─ Anthropic Messages API
            ├─ OpenRouter Chat Completions API
            └─ AIRouter Chat Completions API
```

The Tauri host selects an available loopback port, creates a cryptographically random token, starts the backend without a console window, and owns its process handle. Only a Tauri command exposes the base URL and token to the main webview. The token is not persisted. Production builds package the Python backend with PyInstaller.

## Frontend

The Home access map visualizes selected model routes, permission-scoped resources/actions and
Crew handoffs. Selection traces are configuration previews, not execution telemetry. See
[ADR 0025](docs/decisions/0025-model-map-and-explicit-fallback.md) for route availability semantics
and the opt-in, budgeted local-to-cloud fallback policy.

`src/` contains the React interface. Zustand holds navigation, connection state, conversations, Crew instances, templates, and current model choice. `src/lib/api.ts` is the only backend transport boundary. Pages do not fabricate data; unfinished product areas present explicit empty states.

## Backend

`backend/src/mavo/` is split by responsibility:

- `main.py`: composition, lifecycle, loopback CORS, and API mounting
- `api.py`: typed HTTP endpoints and chat orchestration
- `core.py`: main conversation compatibility and history
- `conversations.py`: independent Core history, per-chat setup context, and atomic deletion guards
- `google_auth.py`, `google_api.py`: native browser PKCE, verified identity, scoped account consent, and DPAPI tokens
- `publisher.py`: bundled public OAuth application identity and developer-mode separation
- `resources/google.py`: shared authorized cache, baseline snapshots, deduplicated domain events
- `google_permissions.py`, `google_actions.py`: exact capability grants, validated action records, execution claims, and provider verification
- `firebase_auth.py`: native Google identity exchange, verified Firebase tokens, workspace ownership, and required session gate
- `action_rules.py`, `desktop_actions.py`: persisted per-assistant policy, scope validation, bounded terminal, dedicated browser, and native Windows tools
- `database.py`: ORM entities, sessions, WAL, foreign keys, and time handling
- `migrations.py`: Alembic startup migrations
- `ollama.py`: local Ollama client
- `crew_planner.py`, `coordinator_contract.py`, `coordinator_client.py`: automatic planning, persisted dialogue, access reconciliation, and dedicated coordinator transport
- `publisher_gateway.py`: separate publisher-funded Minimax service with Firebase authentication, quotas, and response validation
- `browser_proxy.py`: authenticated HTTPS transport with pinned public DNS addresses
- `model_router.py`: provider registry, discovery, and explicit request routing
- `model_routes.py`: legacy migration into user-named provider/model/credential bindings
- `resources/`: adapter contracts and the initial cached weather reader
- `resources/google_extended.py`: read-only Drive metadata/People contacts with persistent per-device daily request ceilings
- `resources/feeds.py`: fixed-source RSS/Atom metadata, safe parsing, shared caches and per-feed revocation
- `connectors/github_auth.py`: publisher-configured native GitHub App device authorization, bounded repository discovery/selection, cancellation and serialized expiring-token refresh
- `connection_revocation.py`: durable non-secret local/provider revocation receipts; the UI never equates credential deletion or user confirmation with a verified provider response
- `resource_pool.py`: one registry of resources, the reads and actions behind each, and the user's access level (off, read, write). The level is a ceiling enforced in action checks and Crew setup; models only see it
- `playbooks.py`: worked scenarios (trip, recurring reminders, inbox, CI, device) that the planner reasons from; data only, grants nothing
- `daily_triggers.py`: validated multiple daily reminder times per Crew, with weekdays and per-trigger messages; legacy single-time Crew keep their delivery keys
- `timeline.py`: read-only upcoming-work projection and the Crew dependency graph
- `resource_access.py`: deny-by-default Weather/Location access flags, revocation cleanup, and collection gates
- `credentials.py`: Windows DPAPI credential protection
- `crew_templates.py`: validated built-in Crew manifest registry
- `crew_engine.py`: per-instance text-session prompts and interrupted-run recovery
- `crew_behaviors.py`: validated template-specific work instructions and default cadence
- `crew_workers.py`: persistent scheduling, leased claims, budgets, cancellation, and checkpoints
- `resources/device.py`: read-only psutil measurements and deterministic alert thresholds
- `reminders.py`: deterministic daily schedule parsing and once-per-Crew/day events
- `security.py`: constant-time session token verification
- `schemas.py`: external request and response contracts

Future modules—resources, signals, Crew, goals, permissions, and entitlements—will live beside these modules and communicate through domain interfaces inside the same process. They will not be separate LLM daemons.

## Persistence

The desktop host sets `MAVO_DATA_DIR` to the platform application-data directory. SQLite runs with WAL, foreign keys, a busy timeout, and versioned Alembic migrations. Conversation, message, and Crew instance IDs are UUIDs. All schema changes must be additive or have an explicit data-preservation migration.

## Model boundary

`publisher_oauth.py` adds a narrow token-exchange route to the existing publisher gateway, not a new service. Packaged Google/Firebase clients use that route when no local OAuth credential exists. It handles only registered client IDs, typed code/PKCE/loopback or refresh grants, fixed Google endpoints and supported scopes. User tokens transit memory but are not persisted on the publisher. Browser authorization, callback ownership and signed identity validation stay in `GoogleAuth`; direct local development with private credentials remains supported. See [ADR 0020](docs/decisions/0020-publisher-google-token-exchange.md).

Mavo supports Ollama, OpenAI, Anthropic, OpenRouter, and AIRouter. OpenAI uses the Responses API, Anthropic uses the Messages API, and OpenRouter and AIRouter use their OpenAI-compatible chat endpoints. Users create named routes that bind one provider, exact model, and opaque credential ID; Crew jobs choose among those routes. Normal chat and setup use a separate publisher-funded AIRouter Minimax service authenticated with the user's Firebase ID token. No provider silently falls back to another, and no fake response is substituted on failure. Credentials are resolved only inside the router and never added to prompts, SQLite, API responses, or logs.

## Planned module boundaries

Optional account providers are registered through server-owned `connectors/catalog.py` metadata and `ConnectorHub`; model routes are a different concern. Existing Google OAuth/resource code remains compatible. Selected GitHub repositories add bounded cached reads and typed actions through the shared audit/permission executor. Catalogs and model schemas omit disconnected or non-consented operations; exact Crew grants and user policies remain additional checks. Credentials stay in the secure store, with non-secret metadata in namespaced workspace JSON. Collection has per-provider/aggregate bounds; leases renew at bounded work phases. GitHub uses interval reviews, not Google-specific events. Microsoft integration was removed in [ADR 0018](docs/decisions/0018-remove-microsoft-connector.md); its startup retirement cleanup runs before workers and preserves other providers and user-created Crew.

- Resource Pool: normalized reads, caching, freshness, and resource authorization
- Signals: deterministic trigger evaluation and durable idempotent job creation
- Crew Engine: persistent bounded workers and isolated checkpoints are implemented; rich scoped memory, resource subscriptions, and action tools remain planned
- Goals: plans, checkpoints, budgets, leases, and bounded resumable work
- Tool/Permission Engine: validated arguments, saved access rules, execution, and outcomes
- Entitlements: capability lookup independent of billing implementation

See [docs/decisions](docs/decisions) for architecture decisions.

## Current work sessions and reminders

`crew_runs` persists work before inference. A partial unique index allows only one running session per Crew, even across competing backend instances. Claims have 180-second leases, longer than the 125-second work timeout. Expired work is recorded as interrupted and running Crew resume from their saved checkpoint. Run/Stop intent, next execution, generation fencing, checkpoints, observations, and daily usage live in SQLite. Stop cancels the local task, marks its claim cancelled, invalidates its generation, and cancels pending reminders. Late results cannot update a stopped or edited Crew. Daily budget reservations are committed with the claim and never reset by Stop/Run or a restart. General leased tool jobs remain future work.

One shared scheduler runs at most two work sessions concurrently per backend. Text workers validate structured checkpoints and either schedule bounded follow-on work, wait for the next review, or pause for input (minimum configurable review interval: five minutes). Each worker step normally uses one model call, with at most one budgeted follow-up for weather or correction of a false missing-browser-tools response. Invalid checkpoints block; transient errors back off, with at most three consecutive attempts. Health and wellbeing prompts receive only their own supplied context. Checkpoints can propose up to three typed actions within exact Crew grants; execution follows explicit saved access rules, with no per-action approval prompts. Computer Crew verifies `device:read` before collecting actual measurements and performs no inference. Hysteresis avoids oscillating threshold alerts. Schedule Crew creates reminders without model calls. All 15 types have explicit behavior profiles; unavailable integrations cannot be enabled by a model.

Google event workers refresh a shared 60-second cache while running, establish a no-event baseline, then process persisted meaningful events using per-Crew cursors. Sender/subject filters run without inference. Unmatched refreshes create no model jobs. Matching snapshots are labelled untrusted data and sent only to the explicitly selected route, subject to the Crew's grants and daily budget. Manual, interval, daily, and resource-event triggers are distinct; general AND/OR Signals rules remain future work.

The coordinator validates structured plans and immediately saves a setup draft, not a registered Crew. Persistent planning sessions support questions, refinement, delegation, and idempotent request IDs. A Crew publishes only after Verify & add, when questions are answered, its own agent connection is configured, and required resource/action access is granted. The model cannot grant OAuth scopes, per-Crew access, or executable tools. Public Google clients are publisher-owned, with their public desktop client ID bundled by PyInstaller. Users grant their own account access through the browser. See [Google setup](docs/google-setup.md) for release requirements and exact read coverage.

The Connect all operation expands only the server-owned Gmail/Calendar/Tasks scope catalog. Consent callbacks verify identity before replacing credentials; failed upgrades preserve the prior connection. Same-account extensions keep sync cursors, partial grants identify missing services, and account changes require disconnection. Start requests are serialized, and cancellation closes owned callback tasks before awaiting the loopback server so a pending exchange cannot block cancellation. Safe error codes replace generic verification errors without exposing provider response bodies.

Daily reminders are a narrow precursor to Signals. The backend scheduler creates due events; while the desktop runtime is open, the frontend checks for delivery every 15 seconds. SQLite deduplicates by Crew and local calendar date. Stopped, paused, unscheduled, and previous-day pending events are excluded from delivery. One overlay is shown at a time; successful dismissal is persisted before closing. Timers may be delayed while Windows or WebView2 is suspended. No model tokens are needed to evaluate or speak a reminder. Preview overlays are explicitly marked and do not create or dismiss real reminder events.

## Publisher coordinator and automatic setup

Resources presents two groups, Default resources and Google Workspace. Weather and device location have independent persisted grants, both off initially. Windows/WebView geolocation runs automatically when Location is enabled or Resources opens with that grant; it has no IP fallback. Location revocation deletes device coordinates and GPS-derived weather state. The backend rechecks permissions after weather requests, and the UI discards late device callbacks. Settings Logout stops authenticated work and clears workspace UI state without implicitly disconnecting Google.

The native status button is sized while hidden, then docked to the monitor work area's bottom-right using physical dimensions and a DPI-scaled margin. Move/resize/scale events clamp it to that work area, and panel collapse restores its prior orb anchor.

`coordinator_contract.py` is the versioned planning boundary shared by the local client and `publisher_gateway.py`. `crew_planner.py` persists conversation leases, exact request fingerprints, decisions, and actual Crew configuration. Creating a Crew never grants model-selected access: after the questionnaire, requested actions may reuse the user's saved defaults with unchanged limits, but existing Crew decisions and resource consent remain separate. Setup receives connection metadata rather than credentials or agent checkpoints. Existing appropriate Crew can receive delegated instructions without creating duplicates.

Core chats each own a `Conversation` linked to one `CoordinatorSession` through a unique nullable foreign key. Messages and planning-Crew context never fall back to another chat. Builder sessions remain separate and need not create chat history. Migration 0014 adds the link without rebuilding existing SQLite tables and preserves the legacy main session, all historical conversations and their messages. New chat/title changes require no model call. Chat deletion atomically rejects a live session lease and cascades only that chat's messages/planning turns, not Crew. Frontend pending/error/input state is keyed by chat ID; late replies never change the selected chat, and logout epochs prevent private response state from returning after sign-out. See [ADR 0019](docs/decisions/0019-multiple-core-chats.md).

The gateway verifies Firebase signatures, issuer, audience, and Google sign-in; reserves daily/minute quotas in persistent SQLite; and invokes a server-selected Minimax model. Request IDs are bound to an identity and payload. Short-lived response caching supports retries. The desktop stores only the public gateway URL. Public release builds reject loopback URLs. The local modular monolith still owns resources, policies, workers, and all tool execution. The gateway is a billing/security boundary for the publisher key, not hosted agent execution.

Action rules are `enabled=false`, `restricted`, or `unrestricted`; custom scopes apply in restricted mode. Platform restrictions, exact grants, generation/revision fences, and budgets always apply. Existing ask-every-time rules migrate to Off. Existing automatic scopes are preserved. Unrestricted Browser HTTPS runs through an authenticated local CONNECT proxy that pins resolved public addresses and blocks private networks. Dedicated profiles are separate per assistant. Stopped or blocked Crew release browser ownership.

Checkpoints may return `question` to pause until a Crew-specific reply, and `notification` to publish a deduplicated desktop update only with `notifications:show`. Inbox spam/trash is skipped before inference. A pending update is suppressed when its notification grant is removed.

Managed browser sessions use isolated persistent Edge profiles per Crew. Actions exposes each operation's defaults and named Crew overrides; explicit Off is not overwritten by refinement. An authenticated sign-in endpoint pauses work and executes the normally authorized open action with a 15-minute generation-bound hold. Browser contention waits without inference. Idle reviews and closed windows release exclusive ownership; no personal Chrome profile, password export, or cookie import is used. Open/click/fill return metadata, while read requires separate permission. `wait_for_next_review` ends a bounded cycle; stable `notification_ids` retain the most recent 1,000 reported item IDs per Crew. See [ADR 0015](docs/decisions/0015-managed-browser-and-action-defaults.md).

The always-present status WebView owns reminder delivery, independently of the main window. Pending durable events are permission-checked, presented one at a time by expanding the existing docked icon, and dismissed in SQLite before clearing native state. Native resize preserves the orb anchor, clamps to the work area, and never explicitly requests keyboard focus. Collapsing is not dismissal. Periodic device status reports coalesce unread older reports from the same Crew; important alert history remains durable.

Computer workers use a typed `DeviceMonitor` in existing configuration JSON, not inference to interpret counters. It selects system health or a local drive's storage counters and alerts/each-check/changes delivery. Drive input permits only system or a drive letter, never paths/UNC URLs. Storage reports include actual free/total GiB (displayed as GB) and free percentage; alerts recover above the low-space threshold plus 1 GB. Failed reads create an explicit needs-input outcome, never invented metrics. These workers consume zero model calls. Legacy explicit drive reports are normalized without changing grants. See [ADR 0016](docs/decisions/0016-device-reports-and-attached-updates.md).

Device observations maintain separate collected-state and published-notification baselines. Only a successfully authorized queued update advances the latter. Changing notification permission clears those delivery baselines without erasing physical threshold hysteresis. Revoking access immediately cancels pending Crew-update events in the same transaction, so rapid revoke/regrant cannot revive stale messages before the next poll. The normal final generation/grant checks still apply to in-flight work.

## Multiple Crew, handoffs and the resource pool

A planning turn may return `crew_proposals` (2 to 8) instead of one proposal. A batch carries no questions: the model asks first, then proposes. Each Crew is still an unverified setup draft with its own access review. `depends_on` names the Crew whose finished result feeds another; the planner rejects unknown names and loops, stores the edges as `configuration_plan.upstream`, and `GET /crew-graph` serves them. When an upstream Crew completes a session, `deliver_handoffs` appends its result to each downstream Crew as untrusted data and wakes it if it is running. Handoff is best effort: a downstream Crew in the middle of its own session can overwrite the note.

The pool (`GET /pool`, `PUT /pool/{resource}`) gives each resource an access level. Off blocks every use, read blocks every action, write defers to Actions rules and per-Crew grants. Defaults preserve existing behaviour (write). Weather and Location keep their existing flags. Lowering a level stops running Crew that depend on what was removed. Open-source candidates are listed as not installed and are never contacted.

The planner context now includes `resource_pool`. A publisher gateway built before this change rejects the extra field, so redeploy the publisher service with this version.

## Staying on

Crew only work while Mavo runs, so a restart of the PC used to stop them silently. Settings has "Start Mavo when I sign in to Windows" (`autostart.py`, `GET/PUT /system/autostart`): one value under the current user's `Run` key, no administrator rights. The installed app registers itself; a development copy (its executable lives under `target\debug`) registers `scripts/start-mavo.ps1`, which starts the assistant service and `dev.ps1` if they are not already up. The app finds its own executable as the nearest parent process called `mavo.exe`. Closing the window only hides it to the tray, so the Crew keep working.

A scheduled Crew (interval or event trigger) only ever stops for the person when it asks a question. If the agent ends a cycle with "waiting for input" but asks nothing, the worker treats it as "wait for the next review"; and on every tick a scheduled Crew parked on "needs input" with no question and no error is resumed (an older version stopped them by mistake). Stored times are UTC and are read as UTC in the interface (`lib/time.ts`).

The desktop icon (`StatusOverlay.tsx`) opens a small menu when the pointer rests on it (about 0.2 s, so passing over does not flicker it) and closes it half a second after the pointer leaves; clicking pins it open and dragging moves the icon. The menu has Open Mavo, Mute (5 min, 15 min, 1 hour) and Quit. Quit asks once, then exits the shell, whose exit handler ends the backend, the browser tools and every Crew's work. Mute (`lib/mute.ts`) only silences desktop pop-ups and voice: the deadline is kept in localStorage (shared by every Mavo window), the icon shows the minutes left, `ReminderWatcher` leaves due updates pending while it lasts and brings them the moment it ends or is lifted. Crew keep working while muted.

## Look and feel

Two themes, one set of names. `styles.css` defines the palette once as CSS variables (`--background`, `--surface`, `--text`, `--accent`, `--ink-rgb` for hairlines and fills, `--z50..900` for the Tailwind grey scale); `tailwind.config.js` points its colours at them, so every class works in Light and Dark. Neither theme is pure black or white, and colour is spent on the accent and on status. `lib/theme.ts` stores the choice (Match Windows, Light or Dark; Settings, Appearance) and sets `data-theme` before anything draws, in every window including the desktop overlays.

Each kind of Crew has a hue and a small living scene (`CrewArt.tsx`, motion in `art.css`): it moves while the Crew runs, rests muted while it is stopped, and wakes on hover. A Crew's result is shown by `Report.tsx`: the agent writes light markdown, and the report turns it into a lead line, notes, tables and record cards (lines like `**Title:** ...`). It never injects HTML and shows links as text. The same component lays out the desktop update card (`DesktopUpdateCard.tsx`): the Crew's name, how long ago ("4m"), the news itself, and Ask, Open (the main window opens on that Crew, passed through shared `localStorage`, `lib/openCrew.ts`) and Done. The worker prompt asks the agent to write in that shape, and a notification to lead with the news, never with what it did (`NOTIFICATION_STYLE`, said just before the alert rule, which stays last).

**Asking a Crew** (`crew_ask.py`, `components/CrewAsk.tsx`, in the Crew panel and on the desktop card): a question goes to Mavo's own assistant (a normal chat turn, `planner.turn`) in a conversation kept for that Crew ("Ask · <name>", also listed in Chat), with the Crew's latest report sent along the first time and whenever it changes, and a standing note to look things up (a one-time task) instead of answering from memory. So it can answer, search and read, run a skill, or ask back. When the turn starts a task, the task's result replaces the interim reply once it is done (`WorkspaceSetting` `asks:<crew id>` keeps the last 20 questions). Measured: "what is the Agniveer scheme?" was looked up and answered from The Hindu's article in 3 model calls; answered from memory, the same model got the facts wrong.

What the person types there is first sorted with one call on the Crew's own connection (`SORT` in `crew_ask.py`): a **standing preference** ("show only jobs") is saved with the Crew (`configuration_plan.preferences`, newest twelve, a contradicting one replaced), confirmed in a sentence, shown as removable tags in the Crew panel, given to every review as rules that override the instructions, and a fresh review starts; anything else is a question and goes to the assistant. Reports are written to `REPORT_STYLE` (labels that fit the item, no empty groups, nothing from the previous report, a note only when it is new), and `tidyReport` in `Report.tsx` hides what only the worker needs ("Next:", "(None)" groups, stray `**`).

**Open data** (`resources/open_data.py`): free public services that need no account or key, which any Crew or one-time agent can look up unless the person turns "Open data" off in Resources. Twenty-two sources: places and travel (Nominatim, OSRM routing, nearby places, sunrise, air quality, India Post pincodes, OpenSky), news and knowledge (Google News, Wikipedia, Hacker News, arXiv, OpenAlex, Open Library, Free Dictionary), money and calendar (Frankfurter, Nager.Date), alerts (USGS, GDACS), developers (GitHub releases, PyPI/npm, Stack Overflow) and Open Food Facts. A Crew returns `lookups` [{source, query, to}] in its checkpoint (a small model often writes them in `actions`; they are moved over); Mavo fetches them with no model, from fixed addresses only (a Crew chooses words, never a URL), politely (Nominatim one a second, with a named User-Agent), cached for ten minutes, and hands back small results marked untrusted with their source. One follow-up call finishes from them; one corrected second round is allowed (`reserve_followup(most=3)`), and an agent still looking after that says it could not finish, with the services' own reasons, instead of passing a "retrying" note off as the answer. A place name is tried as written, then plainer ("campus" dropped, a made-up address cut to "name, town"), then through Photon. A one-time step that only looks things up is an agent with `open_data: true` and no actions. Measured with the user's model: "drive time from Amrita Chennai to the airport" answered 48.2 km, 45 minutes from OSRM, 2 model calls. Overpass and REST Countries were tried and left out (every Overpass mirror timed out from here; REST Countries v3.1 is deprecated).

**People never name tools.** They say what they want; the assistant chooses the workflow. Its instructions list the proven shapes: a question the web answers is skill `web.read` then a writer helper; news is `open_data.gather` (news, wikipedia) then a writer; research is `open_data.gather` (wikipedia, arxiv, papers, books) then a writer; a drive time, place, rate, word, holiday or version is one agent step with `open_data`; anything to watch, repeat or remind is a Crew. Checked with the real assistant: laptops, Agniveer, a drive time and papers each got the right shape. Work at a time of day ("every morning at 8, the AI news") is a Crew that reviews once a day at that time (an interval Crew with `schedule_time`; a daily trigger on a non-schedule Crew is turned into one instead of refused), and the assistant service no longer fails a message whose proposal points at an unrelated existing Crew: it becomes a new draft.

**Building software with a team** (`team_build.py`): "build me a todo list app" is one planner step, skill `team.build`, which the plan expands (`TaskPlan.tidy`) into eight steps: Architect designs it, Coder writes every file as labelled blocks, Mavo saves them in a project (`project.save`), the Tester (Mavo, no model: `app.check`) opens it in a headless browser with the network blocked, catches every script error, presses every button once, and for a list app adds an item and checks it survives a reload (Python is only compiled, never run), the Reviewer reads code, design and test report, the Debugger fixes what was found or says NO CHANGES, Mavo saves the fixes and the Tester tries again; that report is the answer. A web app is one self-contained index.html (projects take no .js files). The build roles get long replies (`model_router.LONG_REPLY`: 16,000 tokens and 300 s; at 4,096 a Pomodoro timer was cut off mid-line), and a file cut off anyway is reported as such. Measured with the user's model: a todo list (215 s, 4 model calls) and a Pomodoro timer (274 s, 4 calls), both working.

The Architect may reply `QUESTION: ...` when something essential is unclear: the task waits with the question on its card (`ask_person`), and the design is made again with the answer (once). Reports and answers may carry LaTeX: `Report.tsx` draws `$$...$$`, `\[...\]` and environments (align, equation, matrix...) as display maths and `\(...\)` or `$...$` holding real maths as inline maths with KaTeX (trust off; prices such as "$0.15 and $3.40" stay text), and a `tabular` as a table, in the app and on the desktop card.

**Scheduled Crews are given only what is new**: Mavo keeps the ids of the mails and feed items each Crew has reported (`observation.seen_items`, marked only once a review has finished) and hands a review only unseen ones, or says plainly that there is nothing new; this was left to the model's memory and an inbox summary repeated the same mails every half hour. A request to be reminded, told, sent or alerted turns desktop alerts on in the proposed Crew (`WANTS_TO_BE_TOLD`).

**Mavo agents** (`mavo_agents.py`), not shown to users: the same six shapes as fixed tasks, reachable with `@web`, `@news`, `@research`, `@places`, `@facts`, `@dev` as an undocumented shortcut. Such a message skips the planning call (`CrewPlanner.mavo_agent`) and starts a fixed one-time task, shown as a task card. Web, News and Research fetch with Mavo's own code (skills `web.read` and `open_data.gather`: no model) and one writer helper answers from what was fetched, citing it; Places, Facts and Developer are a one-time agent with open data look-ups from a short list. `web.read` searches in Mavo's browser, then fetches the result pages at once as plain requests (public https only, checked on every request and redirect; kept to Browser's allowed sites when restricted), uses the browser only for pages that refused, and keeps prose lines only: 7 s instead of 98 s. Measured with the user's model: Web 70 s and News 51 s (one model call each, the time is the model), Research 23 s, Places 23 s, Facts 37 s, Developer 13 s.

**A new update arrives as a pill**, not a window: the status window grows into a one-line pill beside the icon (`status_expanded` with `peek`, 380×72), shows the Crew and the first line of the news, and tucks back into the icon after nine seconds unless the pointer is on it, leaving the attention dot. Clicking the pill or the icon opens the card. `preview.html` (run `vite`, open `/preview.html?theme=light|dark`) renders every card, the report and the desktop card without a backend.

Every page shares one visual language (`studio.css`, `components/Studio.tsx`, `PageHeader.tsx`): a banner in the page's colour carrying one of the Crew pictures (Chat, Crew, Resources, Actions and Settings each have a hue that matches their sidebar tile), colour icon tiles, status chips (on, limit, off, warn), cards that lift under the pointer, and a page that arrives in sequence. Actions are groups you open (a picture, "2 of 11 on", then the rows), resources are picture tiles with one switch, the timeline is a line with coloured dots, and the Crew page has a single way to add a Crew: the first card.

A page tells the browser agent whether the session is signed in only when it can prove it: `sign_in_wall` records `session` as `in` (a sign-out control is visible), `out` (a password field, or a visible "Sign in" button or link) or `unknown`. `browser.open` returns it, and the check behind the Check button after a Crew is added reports "Signed in" only for `in`; a public front page that merely offers "Sign in" is signed out, and a page that shows neither is reported as such, never as signed in. The setup card itself runs no such check: it lists the Crew's sites with an optional "Sign in now", because the agent decides whether a site needs a sign-in when it looks at it ("Try it first" and every run), and a fixed rule cannot tell that as well.

## The browser agent

A Crew's browser work goes through `desktop_actions.py` in Mavo's own browser profile (the user's default browser's engine, a window kept off-screen). `browser.read` returns a compact view a model can act on: headings, tables as rows of columns, text (including text inside open shadow DOM), and every visible control with a stable ref such as `e12` (`f1_e3` inside a frame). Actions take that ref: click, double-click, hover, drag (onto another ref, or by a distance in pixels for sliders and handles), fill, select, press, scroll, wait, plus `browser.navigate {goal}`, which finds a page by name through links, hover menus and account menus without a model call. It follows web links only: `mailto:`, `tel:` and app links (which the browser would hand to the person's mail or phone app, bypassing the request scope check) are never offered or clicked, and a direct `browser.click` on one is refused. It also never clicks anything that deletes, pays, signs out or adds money (`DANGEROUS`), and it stops once it lands on a page named by the goal or a synonym of it. Refs are valid only for the latest read, and a stale one fails with a clear message.

**One-time tasks and helpers (`task_plan.py`, `tasks.py`, `helpers.py`, `automations.py`).** When the user asks for a job to be done now rather than a lasting responsibility ("create a Microsoft form with name and email and tell me the link"), the chat returns `task` instead of a Crew proposal (`CoordinatorDecision.task`). A `TaskPlan` is up to 8 steps; each is a **helper** (a think-only agent: critic, verifier, writer, planner, summarizer; no tools; one model call), an **agent** (a one-time agent that may use tools once), a **crew** step (one of the person's existing Crew handed an instruction) or an **automation** step (a saved script run with no model). `uses` makes it a graph: steps that do not need each other run together (at most 3 at a time), the rest wait. The plan is forgiving where intent is clear (a messy site address, an agent with no actions listed, a repeated id; a loop becomes an in-order chain) and strict only where nothing sensible is left. It starts immediately with no approval of the plan; `CrewPlanner.turn` starts the run only after the turn's transaction is committed (SQLite allows one writer), and a repeated request id replays the same answer without a second run. A run is held to the model-call budget its plan chose, capped at 40, and to 8 steps; `TaskRun` (migration 0016) keeps the plan, each step's progress and answer, and the result.

A one-time agent is a short-lived **hidden** Crew (`CrewInstance.hidden`; never listed, offered for delegation, or shown on the timeline) driven through the same worker as any Crew, so sign-in handling, stale-page handling, budgets and script approvals all apply. Its access is a copy of the person's own **default Actions** (`inherit_requested`), only for what they have turned on: before it starts, `access_problems` says exactly what to turn on in Actions (or which sites to allow for Browser) and the step stops as "needs you" rather than failing; a one-time task never widens the user's settings, and a script run inside it still asks first. The runner drives each agent with `runtime.work`, waits out a busy browser (Mavo has one: steps that use it take turns), waits up to 15 minutes while a script waits for approval (and raises a desktop alert saying so), and deletes the agent when the step ends. A step that stops at a sign-in says where to sign in (`sign_in_url`, the first site it was allowed to open) and the task card offers **Sign in** (opens Mavo's own browser there) and **Try again** (`POST /tasks/{id}/retry`: the stored plan runs again, with no planning call; a sign-in window left open is closed first, which saves its session). Tasks never resume by themselves, so Try again is also what follows turning an action on. **When an agent asks the person something** (a question that is not a sign-in, not a password or code, and not a block Mavo raised itself), the task does not end: the step stays running with `ask` on it, the card shows the question with an answer box, and `POST /tasks/{id}/answer` hands the typed answer to the same agent (`queue_reply`, as a reply in a Crew chat) so it carries on from the page it was on; `ask_person` waits up to 15 minutes, raises a desktop alert, and after that the task stops as "needs you" with Try again. An answer is ordinary chat text for the agent's model, so a question about a password, code, PIN, key or token is **not** asked there: it stops with the instruction to type it in Mavo's own browser (Sign in), where no model sees it. Before starting a task the assistant asks for any detail that decides the answer (where from, a date); a reply that starts a task and asks for such a detail in the same breath is turned into just the question (`held_for_a_detail`), because the task would run without the answer. The result is reported on the desktop by **Mavo itself**, never left to a model to remember: alerts hang on a single hidden "Mavo tasks" Crew, because a reminder needs an owning Crew and the due-reminder query requires it to be active, running and allowed to notify. What the person receives is the work, never a checker's remark: a critic or verifier is never the answer, and its verdict is appended only when it found a problem. Helpers are told that what INPUT says about the present is newer than their own knowledge, so a think-only verifier cannot reject "version 3.15.2" because it has never heard of it.

**Built-in skills (`site_skills.py`).** A model driving an unfamiliar page click by click is slow and, with a small model, loses its way (asked to build a Microsoft Form it clicked and re-read for ten minutes and never typed a word). For jobs people ask for most, Mavo knows the page: a task step of kind `skill` runs Mavo's own code (`microsoft_forms.create` creates a form, titles it, adds short-answer questions and returns the link people answer it at) in Mavo's own browser, with no model call. The planner is told the skills and to prefer them to an agent; a skill step takes its `actions` and `sites` from the skill, never from the plan, so the person's default Actions and site limits still decide whether it may run, and a plan naming a skill that does not exist or parameters that do not fit becomes an agent step that works from the step's instructions. A skill types key by key (setting text in one go shows it on the page, but the page's editor never hears of it, so it is never saved) and reports only after reading the result back from what the site SAVED (after a reload). It stops with a plain reason when the site is not what it expected, and with the sign-in address when only the person can go on. Sign-in is the saved session: Microsoft's account list is answered with the account already signed in, "Stay signed in?" with Yes, and a real password or email box is the person's. Microsoft's sign-in asset hosts (`aadcdn.msauth.net`) are allowed with its sign-in pages, or the page loads blank whenever a job is limited to certain sites.

A Crew can also ask a helper to check its own work (`helper.ask {role, instructions, input}`, group "Agents" in Actions): an action like any other (policy, audit, grant) whose execution is one model call on the Crew's route, charged to the Crew's own step budget through `reserve_followup` (at most one helper per step).

**Saved automations (`automations.py`).** A script run the person approved can be kept so it runs again with no model. Only the person can create one, as an extra choice on the approval of a script run, where they are reading the exact scripts (`RunApproval.automation`). It is tied to the hash of those scripts, tool, window flag and arguments; if any change it does not run, says so, and the person approves the new scripts to save it again. It runs only while Actions are not paused and "Run a script" is on in the default Actions, through the normal action pipeline (so it appears in Activity), on demand, on a schedule checked by the worker loop (not more often than every 5 minutes), or as a task step. Notifications follow the person's choice (never, on failure, every time); a changed or blocked automation always tells them.

**Projects (`projects.py`).** A Crew that is allowed `project.*` can build things on this computer: `project.create` makes a folder under `Documents\Mavo Projects` (the root is the folder saved on that action; the other project actions follow it through `GoogleActions.rule_for`), `project.write` / `project.read` handle text files inside it, and `project.run` runs a script with Python or Blender. Create, write and read are confined to the project and run automatically under the saved access. `project.run` is the exception to "settings alone authorise an action": `ActionRules.automatic` lets it through only when the request was approved by the person (`approved_by = "user"`) or the project is marked trusted (`WorkspaceSetting` `project:<slug>`). When a Crew proposes a run, `GoogleActions.propose` records a hash of every Python file in the project plus the tool, `show` flag and arguments (`WorkspaceSetting` `run:<action id>`); a request for a script that does not exist raises `ActionSlip`, which goes back to the agent as a plain refusal instead of stopping the Crew. The request stays `pending`, the Crew's checkpoint becomes "waiting for your OK" (state `needs_input`, with a desktop notification when allowed), and Actions shows it under "Waiting for you" with the scripts in full (`GET /projects/approvals`). `POST /actions/{id}/approve {sha256, trust}` (the only approve route that is not retired) checks the hash against both the recorded one and the files as they are now, marks the request approved and runs it after the response; the hash is checked once more right before launch. Whatever the outcome (run, denial, failure), `wake_crew` puts the Crew back to `waiting` with `next_run_at` now, so its next step sees the printed output and the files the run changed, and fixes the script and asks again if the exit code was not 0. Files reach a project through the reply, not only through JSON: `parse_checkpoint` lifts every fenced block labelled `file:<path>` out of the reply and hands it to validation as context, and a `project.write` for that path takes its content from the block (the block wins over any `content` in the JSON), because code inside a JSON string is the part small models most often break. A Blender background run passes `--python-exit-code 1` (Blender otherwise exits 0 when the script crashes), and a Blender run with `show` opens its window detached from Mavo's process boundary (the shell's job object allows breakaway) so quitting Mavo never closes it on unsaved work; its messages are read back from a log in the project a few seconds after it starts. Set-all (`PUT /action-policies/bulk`) sets every available action to off, with limits or without limits for the defaults or one Crew, reusing the same validation as saving one action, and reports what it could not set.

Reading waits for the page to settle: it holds a "0 results" skeleton for several seconds, gives up on rotating tickers once the size stops growing, reloads a page that reports its own failure, and can scroll first to load lazy lists. A login, single sign-on page, human check, or a logged-out redirect to the front page is reported as `sign_in_required`, and the worker stops and asks instead of reporting an empty result. Passwords and file pickers are never filled; JS dialogs are accepted unless they warn of something irreversible, and are always reported.

The agent decides about sign-in; the application only notices. `sign_in_wall` flags a login page, a human check or an ended session ("Your session has timed out") and records where its sign-in form is (`login_url`: the page itself, or the same-site "Sign in" link, never another host), but that is a hint handed to the agent with the page, not a stop. In the sample run ("Try it first") and in scheduled work alike, the agent carries on if the page has what it needs, or answers `waiting_for_input` ("Please sign in to ..."). Only then does the sample run open Mavo's sign-in window on the login page, and the panel in the app expands to "Please sign in" and waits; closing the window (or "I've signed in", which closes it politely so the browser saves its cookies) re-runs the test by itself. In scheduled work the first hint gives the agent another turn; if the agent runs into the sign-in a second time, the application stops the run and asks the person. A repeat sample run while the window is open waits instead of opening a second one.

A sample run happens in the background (`POST /crew/{id}/trial/start`, then `GET /crew/{id}/trial` for the stage and result), because the agent's model can take minutes and a request that waits for it would time out. Every browser action has a ceiling (`BROWSER_LIMITS`): a page that never answers is closed and the browser and its lock are released. The sign-in check (`POST /browser/probe`) always answers within a minute; if the site will not, the answer is "unknown" together with `saved_session`, a look at Mavo's cookie store for an unexpired login cookie. Simultaneous checks share one look, and the check is advice that never blocks anything. A sample run opens the first page, then lets the agent ask for up to two named pages (`browser.navigate {goal}`, found through links, menus and account menus like a person would) and reports the way it went as a `trail`: "Opened airouter.in › Found credits (menu → Credits) › Read it and wrote the result". A page that stalls is closed and the run starts once more from a clean browser (`OPEN_LIMIT` and `READ_LIMIT` are shorter than a Crew's, so a stall costs about two minutes, not four) before it gives up. Where a Crew may go is checked by exact host, with one exception: `example.com` and `www.example.com` are the same site (`host_allowed`), because sites redirect from one to the other and a Crew allowed one must be able to read the page it was sent to; every other subdomain is its own host. The sign-in window is always opened inside the screen (`--window-position`, `--window-size`, then moved if the browser put it elsewhere): Mavo's background browser lives off-screen and the profile remembers that spot.

A sign-in has to survive the window being closed. Many sites keep their login in a session-only cookie, and a browser forgets those when it exits, so by default a sign-in made by hand was gone by the time a Crew's background browser started (closing a plain window with the X, or killing it, always loses them). The sign-in window is therefore launched with `--restore-last-session` and a debug port on 127.0.0.1 only (`--remote-debugging-port`, a random free port), and `session_keeper.py` watches it from outside: once a second it asks the browser itself, through the browser-level DevTools socket, for its cookies and re-saves each session cookie with a 30-day expiry (`Storage.getCookies` / `Storage.setCookies`; no page is attached, so sites see nothing different: `navigator.webdriver` stays false, no automation flag, a normal plugin list). The same step runs once more before `Browser.close`, the polite close, when Mavo closes the window. The background browser also restores its last session. `saved_session(host)` reads the cookie store for an unexpired non-tracker cookie when no browser has it open; a running browser locks that file on Windows, so the answer is then `None` ("cannot tell", never "none saved"), and `saved_login(host)` asks the running browser for its cookies instead. These are hints for the agent and the setup card, never a gate: only opening the site proves a sign-in, and a site that shows neither a sign-in nor a sign-out control reads as "likely" when a login is saved, "unknown" otherwise.

Why Mavo's own profile and not the person's default browser: Chromium 136 and later refuses a debug connection to its default profile, its cookies are encrypted for that one browser (app-bound encryption), and sharing them would hand a Crew every account the person has signed in to, not just the sites each Crew is allowed to use. Mavo's own Edge profile is the same engine, holds only what the person signed in to for Mavo, and is the only place the allowed-sites rules can be enforced. A browser extension for the person's own browser is the way to use their real sessions if that is ever needed.

How a recurring Crew checks a site, review after review. A review starts when `automation_steps` is back at zero and ends when the agent returns `wait_for_next_review`; each model step in between is one worker run. (1) Every browser action is keyed to its own step (`step_key`): requests are otherwise matched on crew, operation and arguments so that a retried step never acts twice, and for a browser action that meant an identical `open` or `read` in a later review was answered with the first review's saved page and the site was never visited again. (2) The first step of a review shows the last review's results as `HISTORY`, trimmed and with their age, to compare against and never to report; later steps show only what this review has done (`review_started_at`), and a read older than a later page-changing action is marked out of date. (3) Where a review found its answer is remembered (`learned_page`: the name it navigated by and the page's address) and offered to the next review, which usually needs just an open and a read. (4) The page a batch ends on decides whether there is a sign-in wall: a login-looking page met on the way (many sites look signed out until their sign-in widget has loaded) does not cut a read-only batch short, but a batch never goes on into a click or a form from one. (5) A browser action the Crew was not given (a click, when it has open, read and navigate) is refused to the agent in plain words, up to twice per review, before the person is asked; a site outside the allowed list is the person's to fix and still asks at once. (6) `next_step` may be null: finishing has no next step. Verified on real sites in `tests/browser_agent/RESULTS.md`.

Tests: `tests/browser_agent` runs scripted scenarios against fake sites (`pytest`), `python -m tests.browser_agent.live` runs the same agent on real sites, `python -m tests.browser_agent.login_validation [--profile <a copy of the automation dir>]` checks the sign-in logic on real sites and in the real browser (detection on ten sites, session survival for both ways of closing the window, window placement, and a copy of the app's own profile signed in to its portal), and `model_runs` has a Crew's own model work tasks end to end on a copy of the app data.
