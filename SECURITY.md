# Security and privacy

Cloud fallback is off by default for local agents. Selecting a fallback in a model route's
panel explicitly permits sending that agent's task and permitted data to the chosen cloud
provider using the user's credits. Merely saving a cloud connection grants no fallback access.
Fallback selection is rechecked at claim time, remains budgeted, cannot cascade, and is skipped
if the failing run already started tools. Queued retry metadata is not proof of success. The
animated map previews configured access; use the work/action history for actual outcomes.

Mavo treats local access as a security boundary. A loopback address alone is not authentication.

## Implemented in Milestone 1

- The API rejects non-loopback bind addresses during configuration validation.
- Every sensitive endpoint requires a random 256-bit bearer token created per desktop launch.
- Token comparison is constant-time and the token is passed to the backend only through its environment.
- The webview obtains the token through a Tauri command; it is not stored in local storage or the database.
- CORS uses an explicit origin list and never permits wildcard origins.
- Tauri applies a restrictive content security policy.
- Ollama endpoints are restricted to unencrypted loopback HTTP, preventing configuration-driven SSRF.
- Chat model names and message sizes are schema validated.
- SQLite foreign keys, migration history, and WAL are enabled.
- Telemetry is absent; stored conversations are local. Selected cloud model routes receive their request context.
- Backend logs exclude request bodies and credentials.
- Cloud API keys are DPAPI-encrypted for the current Windows user and stored outside SQLite.
- API responses expose only whether a credential exists, never the credential value.
- Normal chat uses the publisher-funded coordinator. Agent work uses the selected user connection; neither silently falls back to the other.
- Crew workers check grants in code, use isolated checkpoints, reserve daily call budgets atomically, and reject overlapping claims.
- Device metrics require an explicit `device:read` grant on a Computer Crew; revocation cancels its work and prevents future collection.
- Stop invalidates a worker generation so a late model response cannot update stopped work. Google reads require account consent and separate per-Crew grants. Actions require exact grants and durable proposals, authorized only by exact saved user access settings.
- Google sign-in uses system-browser PKCE, a random-port loopback callback, state/nonce validation, and verified signed OpenID tokens. Refresh tokens are DPAPI-protected and never returned to the frontend.
- Publisher desktop client identity is public and bundled once; web secrets and service-account keys are never bundled. Developer client editing is off by default and cannot override publisher identity.
- Model Crew proposals pass strict schemas; Crew creation is automatic; only a user action grants resource/action access. Missing access or setup answers prevent activation.
- Destination weather requires both global Weather and per-Crew `weather:read`, not Location. Model-requested lookups cannot read device coordinates or overwrite preview settings. At most three reads and one additional budget-reserved model call are allowed; intermediate notifications/actions are not executed. Revocation fences results and stops weather-enabled Crew.
- Firebase login is required on workspace endpoints as well as the local bearer token. Verified Firebase identities bind the workspace to one account; sign-out stops work and rejects pending approvals. Credentials remain DPAPI-protected.
- Google actions use strict operation/argument schemas, fixed endpoints, atomic execution claims, account and Crew-generation checks, bounded leases, and provider verification. Unknown outcomes are never automatically retried. A send acknowledgment is not proof of delivery.
- Google write consent does not grant write access to every Crew. Sending, mailbox changes, Calendar writes, and Tasks writes are separate per-Crew permissions. Models cannot approve actions or expand grants.
- Actions start disabled. Policies are independently scoped to manual tools or a Crew and fenced by revision. Restricted access enforces custom scopes; unrestricted access still enforces budgets, exact account/Crew grants, operation schemas, and platform restrictions. Sending in restricted mode requires configured recipients. No per-action approval endpoint remains available.
- Terminal has a fixed command catalog, no shell or arbitrary arguments, an approved folder, a reduced environment, disabled Git hooks/fsmonitor, and bounded time/output. The terminal itself never runs code. The one place Mavo runs code is a project run, below.
- Projects (`project.create/write/read/run`). Files live in a Mavo-made folder (default `Documents\Mavo Projects`, changeable on "Create a project folder"). Writing is confined to the project: plain relative names only (no `..`, drives, device names or hidden names), no symlinks or junctions followed (listings, hashes and previews never enter one), text file types only (no `.bat`, `.exe`, `.ps1`, `.dll`, `.lnk`), 200 KB per file, 200 files and 5 MB per project. Nothing there executes.
- **Running a script is the one step that executes code, and it is not sandboxed.** A run uses Python or Blender (`blender --python`) with the person's own Windows rights; Mavo cannot confine what a script does, least of all inside Blender. The controls are therefore about consent and blast radius, not isolation: (1) every `project.run` waits for the person, who is shown the entry script and every other Python file in the project; (2) the approval is bound to a SHA-256 of all of those files plus the tool, window flag and arguments, recorded when the run was requested and checked again when the person approves and right before launch, so a script cannot change between "reviewed" and "run" (the server, not the model, computes it); (3) a person may mark a project trusted so its runs go ahead without asking, and can withdraw that at any time; (4) "Allow without limits" does not skip the approval; (5) only `python.exe` and `blender.exe` can be named as tools, the tool is chosen from a fixed list and never a model-supplied path, and arguments cannot carry interpreter options (Python gets `-E -s`, Blender gets them after `--`); (6) the run's environment is reduced to what a program needs to start, with no keys, tokens or Mavo variables; (7) time (2 min Python, 10 min Blender) and output are bounded and the process tree is killed on timeout, stop or sign-out; (8) a Blender window opened with `show` breaks away from Mavo's process boundary so quitting Mavo does not close it on unsaved work, and its messages are written to a log in the project. Treat an approved script like any program you chose to run: read it first.
- One-time tasks and helper agents. The chat may start a task immediately, without the person approving its plan, because a task has no powers of its own: a **helper** has no tools; an **agent** is a short-lived hidden Crew whose access is a copy of the person's own default Actions, only for what they have turned on (it can never exceed those settings, and pausing Actions stops it); a **crew** step uses an existing Crew's own access. Script runs inside a task still need the person's approval. A task has a hard budget (at most 8 steps and 40 model calls; the model chooses within that) and runs at most 3 steps at a time. Agents are deleted when their step ends, and text from earlier steps reaches a later step as untrusted data. Trade-off, stated plainly: because the source of access is the default Actions, a person who has set them to "without limits" (for example with Set all) lets a one-time agent act on any site with no per-task prompt; what remains is the budget, the per-run approval for scripts, and the fixed refusals (never passwords, never other programs).
- A Crew may ask a think-only helper to check its work (`helper.ask`): no tools, one model call, charged to the Crew's own step budget.
- Saved automations: only the person creates one, on the approval of a script run, while reading the exact scripts. It is bound to their hash and runs unattended only while they are unchanged, Actions are not paused and "Run a script" is on; otherwise it stops and says so. Agents cannot create, edit or approve one.
- The access settings for browser, terminal, window, project and mail actions can be set for every action at once (off, with limits, or without limits) for the defaults or for one Crew. Without-limits needs an explicit confirmation, an action that still needs a site, folder or app list is left as it was and named, and none of it removes the approval step for script runs.
- Browser uses a dedicated Edge profile per assistant and a reduced process environment and public HTTPS host allowlist with pinned addresses. Downloads, popups, WebSockets, password/file inputs, and arbitrary model JavaScript are unavailable. Links that start another program (`mailto:`, `tel:`, an app's own scheme) are never offered or followed, because the browser would hand them to the operating system outside the request scope check. Drag and drop, hover and double-click act on the page like a click and are granted separately. Bounded page text and selectors remain untrusted content.
- Windows control checks approved app names, process creation times, handles, and foreground identity before input. It cannot elevate privileges or infer arbitrary screen coordinates. Foreground input remains subject to Windows focus restrictions and user interaction.
- Pause/sign-out stop work and close owned desktop tools. Quit first requests authenticated tool cleanup, then terminates the sidecar. Closing the main window hides it while tray/status controls remain visible. A Windows Job Object owns the managed process tree and terminates descendants if the desktop host exits or crashes.
- Google disconnection removes tokens, cached resource snapshots/events, and Google-derived worker results; affected Crew stop with generation invalidation. Removing the remote OAuth grant is available through Google account connections.
- Weather and Location are independently denied by default and enforced in backend code, including checks after external requests. Device location is detected automatically only after Location is enabled, also requiring Windows/WebView permission. Coordinates are rounded to three decimal places, with reported accuracy retained; no IP fallback bypasses denial. Revoking Location removes saved device coordinates and invalidates weather cache. Destination queries use city/state/country to avoid ambiguous first matches. The Resources UI detects computer location automatically without manual setup controls.
- The Vite development server denies `.build` and backend files, including database backups; temporary browser debugging is never enabled by normal launch scripts.

The unauthenticated `/health` route returns only `{ "status": "ok" }`, which exposes no configuration or data.

## Trust boundaries

Account connections are optional and provider-scoped. Firebase app login never grants Google Workspace or GitHub access. Actions and worker schemas omit disconnected providers and operations without matching scopes. GitHub tokens are encrypted and constrained to explicitly selected repositories, even when custom action limits are removed. A provider's 401/403 invalidates rejected access and fences affected work. Account consent and per-Crew grants remain separate. Microsoft OAuth, API dispatch, tool schemas and native authorization URL support have been removed. Upgrade cleanup deletes its exact stored token/metadata and saved policies, rejects pending actions and stops affected Crew without deleting those Crew, chat or other connections. Historical audit records are retained; local credential deletion does not revoke a grant at a remote provider.

Packaged Google/Firebase sign-in exchanges and refreshes tokens through the existing publisher service when no local OAuth credential is configured. The publisher supplies its server-only credential for exact allowlisted Desktop client IDs; it cannot act as a generic token/HTTP proxy. Native PKCE/state/nonce and signed identity verification remain mandatory. Bootstrap uses Google's code/PKCE or a private refresh token, not a prior Firebase session. It has fixed scopes/redirect validation, separate persistent rate limits, bounded bodies/concurrency, denied browser Origins and no reflected validation inputs. Credentials transit the publisher over HTTPS (or development loopback), never its persistent quota store/logs; responses are non-cacheable and desktop tokens stay DPAPI-protected. This flow must be disclosed; anonymous bootstrap is not proof of an official binary. A public deployment needs TLS, trusted proxy and abuse controls.

GitHub PR and workflow/CI reads are separate account/Crew opt-ins. They return bounded metadata, not PR bodies/diffs, source code, job logs or artifacts. They do not enable merge, workflow execution or other new writes.

Google disconnection does not cancel/redact GitHub actions. GitHub disconnection clears its credentials/cache, stops and fences affected Crew, removes its grants, and redacts derived output and action payloads. Account changes require disconnection. External actions use shared typed validation, account binding, exact grants, policy revisions, generation fencing, durable claims and no automatic replay of uncertain writes. See [the provider guide](docs/providers/README.md).

Device monitoring reads OS counters only after `device:read`; notifications need a separate `notifications:show` grant, rechecked before publication and delivery. Typed storage settings accept only system or local drive letters, not arbitrary paths or network shares. Checking low disk space does not authorize enumerating/deleting files, running cleanup, or changing Windows settings. The desktop message's Check now and Stop buttons affect only its originating Crew; Dismiss only acknowledges the notification. The attached status panel renders messages as text, not executable HTML, and does not automatically perform proposed consequential actions.

Notification revocation immediately cancels pending Crew updates instead of relying on a later desktop poll. A subsequent grant does not resurrect those cancelled events; a fresh authorized check may publish a new status. Device collection while notifications are denied does not advance the published-alert baseline. These transitions, late-result fencing, and in-flight stop/delete/pause/revocation are covered by isolated lifecycle tests.

Saved manual action rules also serve as explicit defaults for new description-based Crew. Only requested operations are copied, with unchanged scopes; existing Crew overrides (including Off) are never overwritten. Models cannot widen limits or copy Google account grants. Expanding an action shows each Crew's independent access by name.

Mavo browser sign-in pauses the selected Crew and uses the normal saved `browser.open` policy and audit path. A generation-bound hold keeps its window open for at most 15 minutes; revocation, sign-out, or pause still closes it. Browser profiles are separate per Crew and never copied from Chrome. Session cookies/local storage persist in the local automation directory and should be treated as sensitive local data; that directory is not an encrypted vault. No password export, cookie export, or browser token import is accepted. Enter passwords only in the actual website, not chat. Opening/clicking/filling returns page metadata, not body content; reading requires its own action grant. Website text is untrusted model input.

Model output is untrusted content and rendered as plain React text. Crew configurations need schema validation; resource and action grants require explicit user settings. When a cloud provider is selected, conversation context and explicitly authorized Google event snapshots are transmitted to that provider under the user's account and provider terms. Gmail headers, calendar entries, tasks, and future retrieved content remain untrusted data and cannot grant permissions or execute instructions.

OAuth tokens and model API keys are encrypted; the SQLite database itself is not encrypted. Google snapshots, Crew output, and chat text are stored locally in SQLite. Disconnection does not erase user-entered Google information from ordinary chat history or copies already sent to providers. Public Gmail distribution requires the applicable Google verification, including assessment of cloud model data flows; see [publisher setup](docs/google-setup.md).

## Future requirements

Connection cards expose requested access before consent and actual saved grants afterwards. Normal GitHub connection can automatically commit one to ten repositories explicitly shared through GitHub; more than ten require selection. Installation discovery is bounded to five minutes and does not invoke an LLM. No token forms or unchecked arbitrary-repository defaults are exposed in Resources. Crew and Actions checks remain mandatory.

Explicit Revoke access clears local credentials and fences/removes account grants before waiting on remote requests. Google revocation is fixed-endpoint, bounded and confirmed only on HTTP 200. GitHub's secretless desktop flow opens Authorized GitHub Apps for user removal; a recorded user confirmation is not mislabeled as a provider-verified API receipt. Signed-out sessions cancel pending Google and GitHub flows. Reconnection does not restore revoked Crew grants. Ordinary user-entered conversations and descriptions are retained.

GitHub browser connection uses the publisher's public GitHub App ID/slug and standard device authorization, not a bundled client secret/private key. Device codes and uncommitted tokens stay in memory; repository selection is verified before DPAPI storage. Pending flows cancel/expire and are fenced on disconnect, logout and shutdown. Refresh is serialized and checks for intervening credential changes before rotating tokens. Rejected/revoked authorization stops affected work. Selected repositories remain a hard boundary under every Actions mode. GitHub App authorization does not imply unlimited GitHub features or grant every Crew access. The current per-Crew capability grant covers the connection's shared selected-repository set, not independent per-Crew repository selections.

Drive metadata and saved Contacts are independently consented read-only resources. No file contents, downloads, account directory or contact writes are exposed. The current metadata grant is account-level, not folder/file isolation. Both enforce cached authorization, account-epoch fencing and a persistent 200-HTTP-request per-device/service/day ceiling; this does not cap a shared publisher project's billing. Their SQLite snapshots can contain private names, email addresses and phone numbers; DPAPI protects tokens, not those snapshots. Public Drive scope verification and model-provider disclosures remain release requirements.

Public feeds are opt-in fixed HTTPS sources, not arbitrary URL fetches or executable plugins. Redirects and XML DTD/entities are rejected; size/time/item/cache limits apply. Each source requires a separate Crew grant. Revocation stops/fences affected workers, removes the grant and clears checkpoints/observations, but historical work receipts can retain public titles. Data is never treated as authority to grant permissions or execute instructions.

Broader account sync, database encryption, and granular historical-data deletion remain future work. SQLite also stores action proposals and audit outcomes, including authorized content. Google disconnection redacts saved action payloads and outcomes.

Health and wellbeing resources require purpose-specific authorization. Coding tools will be limited to explicitly approved repositories. Isolated (sandboxed) execution of project scripts, such as Windows Sandbox or an AppContainer, remains future work; until then a project run relies on the person's approval. Revocation must immediately prevent new access and queued work.

## Reporting vulnerabilities

Until a public security contact is established, do not disclose exploitable details in a public issue. Repository maintainers should add a private reporting address before the first release.

## Publisher-funded chat

The shared AIRouter key stays on the separate publisher server (Windows DPAPI for local testing, server-only secret configuration for hosting). It is never stored in the desktop bundle or returned through the API. Firebase tokens gate every paid turn. Per-account/global daily limits, per-minute limits, concurrency bounds, output limits, and identity-bound request IDs limit cost exposure. A public `/health` response exposes no credentials. A live authenticated request is required to verify provider credit and model availability.

The coordinator receives conversation/setup text, Crew descriptions and connection metadata. It does not receive agent keys, inbox bodies, or agent checkpoints. Private health/wellbeing descriptions are redacted from the general Crew index; explicitly editing such a Crew shares its setup. Cloud processing must be disclosed to users before public release. Server response caching is ten minutes; quota metadata expires after seven days. See [publisher deployment](publisher/README.md) for storage and deployment boundaries. No public server/domain has been provisioned automatically.
